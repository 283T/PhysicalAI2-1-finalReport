## 目標・固定事項

Mac＋Dockerを維持する。動画の長さと倍率は**実時間記録**を基準にし、物理時計を使って早回し倍率を小さく表示しない。
目標は一連動作の実時間を約40分から5分以内へ短縮し、説明込み3分・最大2倍速・動作区間のカットなしに近づけること。
約8倍の改善が必要で、達成は未保証。描画・カメラ・録画を有効にした最終構成で判断する。

提出済みPDF・YouTube・omnicampusと、正式Bの2成功／3試行は保存する。
旧全接続Goalは未達。速度改善は別の開発実験で、正式Bの結果へ後から加えない。
評価閾値（上昇70 mm超、滑り5 mm未満、回転0.05 rad未満、4物理秒保持）を緩めない。
提出済みmainのworld・制御候補を維持し、改善コードは専用ブランチcodex/mac-docker-performance、実験入力は別コピーで管理する。実行中の制御ソース変更・二重起動を禁止。

## 開始時点で確認した環境

- Docker VM：8 CPU、約8.32 GBメモリ（docker infoの値）。GUIサービス共有メモリ512 MB。
- Gazebo 8.15.0 / ROS 2 Jazzy、Dockerfileはソフトウェア描画を強制。
- 基準world：物理刻み0.0001秒、保存シーン54リンク・49関節・216衝突形状。
- RGB-D：640×480・5 Hzが1台、1920×1440・1 Hzが2台。
- 正式Bのログには物理14.71秒／実366.83秒の移動区間がある。
- 改善開始前に既存のGazebo・制御・ROSブリッジが残っていないことを確認した。

## 工程

| 段階 | 実施内容 | 判断基準 |
| --- | --- | --- |
| 1 基準測定 | 既存worldの初期状態で短い固定物理時間の統計を取得。GUI＋カメラ＋録画を基準に比較 | 実時間、物理時間、反復数、CPU/RSS参考値を保存。起動待ちは別計測 |
| 2 負荷切り分け | 録画だけ停止→GUIも停止→画像センサー停止を一つずつ比較 | 初期シーンの負荷寄与を示す。把持中や全工程の高速化へ一般化しない |
| 3 画像軽量化 | 効果がある場合、必要工程だけカメラ起動・高解像度削減・録画表示の軽量化 | 新規RGB-D安定3枚、位置・姿勢照合の精度を再検証 |
| 4 通信・記録 | 重複処理、不要な配信、細かなファイル書き込みを計測して整理 | 監視の欠落・情報の古さが増えない。全把持検証に必要な証拠を保存 |
| 5 物理計算 | 衝突形状の簡略化と刻み0.1→0.2→0.5 msを個別比較 | 貫通・振動・滑り・保持失敗を拒否。変更前後の差分・失敗を保持 |
| 6 一連再検証 | 候補を固定し、新規3試行と実時間基準の連続録画を実施 | 全結果・成功数・描画認識録画込み実時間を報告。録画の欠落も検査 |

## 最初の測定プロトコル

比較対象は同じ保存初期world、同じ0.1 ms刻み。操作なしの初期シーンに限定し、把持成功率や制御負荷を測定するものではない。
新しい初期状態から起動し、1物理秒ウォームアップ後に3物理秒以上を測定する。
Gazeboのnative statsから物理時間・反復数、ホスト単調時計から実時間を取得する。
最初は各構成1回の探索。順序・キャッシュ・負荷変動の影響があるため、採用候補は反復して判断する。

1. GUI・全画像センサー・5fps実録あり。
2. GUI・全画像センサー、録画なし。
3. headless・全画像センサー、録画なし。
4. headless・画像センサーなし、録画なし。接触センサーと物理モデルは維持。

4は負荷下限を調べる診断で、提出用の最終構成として採用しない。認識・録画を戻した状態での検証が必要。
worldの差分とSHA、全統計、失敗、プロセス所有情報・終了確認を保存する。
実験待機には上限を設け、失敗を成功値として集計しない。
