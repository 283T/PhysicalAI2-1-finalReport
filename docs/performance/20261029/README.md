# Mac＋Docker速度改善：最初の実測（2026-10-29）

[計画](../../performance-plan-20261029.md)に基づく探索。Docker VMは8 CPU・約8.32 GBメモリ、共有メモリ512 MB。
既存の提出済み正式B・動画・PDFは変更していない。制御ソースSHAは正式B候補と一致する。

## 初期シーンの負荷切り分け

同じ保存world、刻み0.1 ms。操作なしで1物理秒ウォームアップ後、約3物理秒を測定した。
各1回、記載順に実行。把持中・ROS制御ありの全工程性能へ一般化しない。

| 構成 | 測定物理秒 | 実時間秒 | RTF（物理秒／実秒） | 基準比 | CPU参考コア |
| --- | ---: | ---: | ---: | ---: | ---: |
| GUI＋全カメラ＋録画 | 3.0015 | 44.74 | 0.0671 | 1.00× | 3.64 |
| GUI＋全カメラ、録画なし | 3.0002 | 47.48 | 0.0632 | 0.94× | 3.62 |
| headless＋全カメラ | 3.0104 | 30.76 | 0.0979 | 1.46× | 1.08 |
| headless、画像センサーなし | 3.0085 | 29.96 | 0.1004 | 1.50× | 1.04 |

録画停止だけでは改善しなかった。GUI停止は約1.46倍、そこから画像センサー停止の追加は約1.03倍だった。
順序・キャッシュ・負荷変動を分離する反復は未実施。録画停止が常に遅くなる、カメラが全工程で無負荷、とは結論しない。
初期の予想と異なり、この場面では画像センサー停止だけで大幅改善する根拠は得られなかった。
GUIありのCPU合計は約3.6コア、headlessは約1.0コア。CPU値は所有プロセスのtick差分で、厳密なプロファイラの内訳ではない。

## 物理刻みの探索

GUI・全カメラ・5fps録画を全て維持し、コピーしたworldの物理刻みだけを変更した。
XMLを元と照合し、元入力が変更されていないことを確認した。

| 刻み | 測定物理秒 | 実時間秒 | RTF | 0.1 ms基準比 |
| --- | ---: | ---: | ---: | ---: |
| 0.1 ms | 3.0015 | 44.74 | 0.0671 | 1.00× |
| 0.2 ms | 3.0010 | 26.69 | 0.1124 | 1.68× |
| 0.5 ms | 3.0025 | 10.62 | 0.2828 | 4.22× |

これは物理計算量の削減に効果があるという探索結果。数値安定性・把持成功・全工程の5分達成を示す結果ではない。
出力統計を独立に再計算し、実時間・物理時間・反復数×刻みの一致、測定中unpaused、終了後の所有プロセス消滅を確認した。
生統計・ログ・worldの可逆gzip・SHA manifestは各`ablation_r01/`、`step_0002_r01/`、`step_0005_r01/`へ保存した。

## 次：0.5 msの一連開発試行

`pickup_dt0005_registry.json`へ実行前に1試行を登録した。対象は同じD101・配置2・P3、右端子／左ワイヤー支持・持上げ・保持。
元の物理刻み0.1 msから0.5 msへの変更以外は維持する。カメラ・GUI・録画も有効、閾値の変更なし。
終了後に全把持ログ、保持物理時間、監視対象接触、実時間、録画の連続性を確認する。
失敗は保持する。正式Bの2成功／3試行へ後から追加せず、成功しても新しい正式3試行の代わりにしない。

## 再実行

`benchmark.py`はGazebo環境内で動作し、新しい出力先を要求する。
元worldなどを復元する方法は`docs/reproduce-submission.md`。既存のシミュレーション・制御がない状態で実行する。

```bash
docker compose exec -T gui bash -lc 'source /opt/ros/jazzy/setup.bash && python3 docs/performance/20261029/benchmark.py --world outputs/stepped_nest_contacts_hd_20261016/case/world.sdf --output outputs/performance_ablation_new'
```

`--cases gui_capture`で基準だけを実行できる。ベンチマークはロボットの制御を実行しない。
