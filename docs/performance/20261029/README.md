# Mac＋Docker速度改善：最初の実測（2026-10-29）

[計画](../../performance-plan-20261029.md)に基づく探索。Docker VMは8 CPU・約8.32 GBメモリ、共有メモリ512 MB。
既存の提出済み正式B・動画・PDFは変更していない。制御ソースSHAは正式B候補と一致する。

## 初期シーンの負荷切り分け

同じ保存world、刻み0.1 ms。操作なしで1物理秒ウォームアップ後、約3物理秒を測定した。
各1回、記載順に実行。把持中・ROS制御ありの全工程性能へ一般化しない。

| 構成 | 測定物理秒 | 実時間秒 | RTF（物理秒／実秒） | 基準比 | CPU参考コア |
| --- | ---: | ---: | ---: | ---: | ---: |
| GUI＋全カメラ＋録画 | 3.0015 | 44.74 | 0.0671 | 1.00× | 3.64 |
| GUI＋全カメラ、録画なし | 3.0002 | 47.48 | 0.0632 | 0.94× | 3.62 |
| headless＋全カメラ | 3.0104 | 30.76 | 0.0979 | 1.46× | 1.08 |
| headless、画像センサーなし | 3.0085 | 29.96 | 0.1004 | 1.50× | 1.04 |

録画停止だけでは改善しなかった。GUI停止は約1.46倍、そこから画像センサー停止の追加は約1.03倍だった。
順序・キャッシュ・負荷変動を分離する反復は未実施。録画停止が常に遅くなる、カメラが全工程で無負荷、とは結論しない。
初期の予想と異なり、この場面では画像センサー停止だけで大幅改善する根拠は得られなかった。
GUIありのCPU合計は約3.6コア、headlessは約1.0コア。CPU値は所有プロセスのtick差分で、厳密なプロファイラの内訳ではない。

## 物理刻みの探索

GUI・全カメラ・5fps録画を全て維持し、コピーしたworldの物理刻みだけを変更した。
XMLを元と照合し、元入力が変更されていないことを確認した。

| 刻み | 測定物理秒 | 実時間秒 | RTF | 0.1 ms基準比 |
| --- | ---: | ---: | ---: | ---: |
| 0.1 ms | 3.0015 | 44.74 | 0.0671 | 1.00× |
| 0.2 ms | 3.0010 | 26.69 | 0.1124 | 1.68× |
| 0.5 ms | 3.0025 | 10.62 | 0.2828 | 4.22× |

これは物理計算量の削減に効果があるという探索結果。数値安定性・把持成功・全工程の5分達成を示す結果ではない。
出力統計を独立に再計算し、実時間・物理時間・反復数×刻みの一致、測定中unpaused、終了後の所有プロセス消滅を確認した。
生統計・ログ・worldの可逆gzip・SHA manifestは各`ablation_r01/`、`step_0002_r01/`、`step_0005_r01/`へ保存した。

## 一連開発試行：0.5 msは現時点で採用しない（10/30更新）

登録後の1試行は右腕のprimary_hoverで `simulation_budget_exhausted before robot convergence` により失敗した。
録画を含む実時間201.754秒で終了。把持・持上げには到達していない。
終端観測で右手首の関節誤差は0.01125995 radとなり、既存の0.01 rad未満という収束ゲートを超えた。
経路終端まで指令した状態で時間予算が尽きたことと、最後のゲート違反を独立再計算した。
この1回だけで数値誤差の全原因や失敗率を断定しないが、短区間の4.22倍だけを根拠に採用することはできない。
閾値・時間予算・制御ソースを変えず、失敗と原録画を保持した。監視した元ソースに変更なし。
保存先は`pickup_dt0005_failure/`。把持前の失敗のため、保持・全把持ログの成功を主張しない。

実行中の10実秒のCPU参考値はGUI約2.70コア、制御Python約1.05、Gazeboサーバー約1.00、FFmpeg約0.049、ROSブリッジ約0.076。
厳密な関数プロファイルではないが、録画エンコードが主なCPU消費という根拠はない。
追加のnative stats診断は環境読み込み不足で1回失敗し、再試行は終了後で標本0だった。速度ゼロの測定値として扱わない。

次は0.1 ms・全カメラ・録画を維持し、GUIのサイズだけ800×600へ下げる比較を行う。
1280×900→800×600→1280×900の順で探索し、サイズ変更の実映像と順序変動も確認する。

## GUIサイズ比較（10/30）

物理刻み0.1 ms・全カメラ・5fps録画を維持。1280×900→800×600→1280×900の順で測定した。

| 順番・描画サイズ | 実時間秒（約3物理秒） | RTF | CPU参考コア |
| --- | ---: | ---: | ---: |
| 1：1280×900 | 49.77 | 0.06031 | 3.69 |
| 2：800×600 | 42.72 | 0.07038 | 3.17 |
| 3：1280×900 | 49.62 | 0.06055 | 3.72 |

800×600は前後の元サイズの平均に対して約1.165倍（約16.5%の速度向上）。GUIが実際に縮小したことも原録画のフレームで確認した。
物理条件を緩めずに減らせる負荷として候補を保存したが、この差だけでは5分以内に届かない。
映像は試験用に1280×900の画面を録画したため未使用領域を含む。提出動画ではなく、認識用カメラの解像度を変えた実験でもない。
統計・SHA・前後の結果は`gui_size_*`と`gui_size_comparison.json`。一連動作をこのサイズで再評価した結果ではない。

### 次の工程

1. 元の0.1 msと小さいGUIを候補にし、制御Pythonの処理時間を短い診断で関数別に計測する。
2. 新鮮さ・接触監視を維持したまま、重複した計算や配信を減らせる箇所を特定する。
3. 必要なら0.2 msを別の短い収束診断から検証する。0.5 ms失敗の基準を緩めて再採用しない。
4. 有効な変更をまとめた候補ができてから、一連動作・実時間基準の連続録画・新規3試行へ進む。

この段階の結果は「安全に使える約8倍の高速化が達成済み」ではない。5分以内という目標は未達。
