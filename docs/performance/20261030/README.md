# 制御Pythonの計測と計算最適化（2026-10-30）

改善専用ブランチ `codex/mac-docker-performance` で開発する。提出済みmain・動画・PDF・omnicampusは変更しない。
Mac＋Docker、元の物理刻み0.1 ms、800×600 GUIを維持。全工程5分以内という目標は未達。

## 計測方法と失敗の保持

`profile_controller.py` は初期位置を保持する短い制御ループの診断。把持・移動・接続の成功試行には数えない。
各回は10実秒の非プロファイル窓と10実秒のプロファイル窓。関節・姿勢・接触の監視は元のまま。
主スレッドはcProfile、native受信コールバックは別の軽い経過時間計測とした。
計測器自体が速度へ影響するため、物理速度の比較には非プロファイル窓を使う。コールバック時間はCPUの厳密な内訳ではない。

最初の計測は複数cProfileインスタンスの競合で受信処理が失敗し、Lost feedbackとなった。
これは計測器の不具合。`failed_profiler_r01/`へ元の計測コード・失敗結果・可逆gzipのログを保存し、正常測定へ混ぜない。
修正後の各計測コードはmethod_sha256と一致する版を各フォルダへ保存した。

## 分かった重い処理

元実装のプロファイル窓10秒では、snapshotが累積8.259秒、その内側のforwardが7.159秒、軸回転計算が4.134秒だった。
同じ指令に対しても、複数のsnapshotごとに順運動学を再計算していた。

変更は次の2点。

- URDFの固定軸のRodrigues係数と単位行列を構築時に準備し、毎回の軸正規化・行列準備を削減する。ヤコビアン不要時の中間量も作らない。
- 指令姿勢だけを、指令関節値・モデル・base/toolが同じ場合に再利用する。実測姿勢・新鮮さ・搬送台・接触監視は毎回実行する。

キャッシュから渡す証拠は独立したリストで、呼出側の書換えがキャッシュを汚染しない。指令のin-place変更、base/tool変更で更新する。
これは計算の重複削減であり、監視頻度や閾値を下げる変更ではない。

## 数値・回帰検証

- 保存した元実装と左右MELFA各1,003姿勢、計2,006姿勢の位置・回転・ヤコビアンを比較。最大差はいずれも0、検査許容値1e-12。
- 順序を交互にしたFK単体3回の速度比：2.894／2.948／2.853倍。
- 斜め軸の既知120度回転とヤコビアン差分、指令変更、証拠の独立性、base/tool変更、古いフィードバック拒否を追加検証。
- Docker内の全274テストが通過。実際の把持・保持・一連動作を新候補で通過したとは扱わない。

`fk_comparison.json`、`tests_274.log`、`compare_kinematics.py`を参照する。

元方式は元のFKカーネルと指令姿勢の非キャッシュを使う。残りは現行の同じsnapshot枠組みであり、元ソース一式の完全リプレイではない。

制御tickの処理能力やFK単体速度を、シミュレーション全体の高速化へ読み替えない。

## メッシュ衝突の診断：採用しない

14個の腕の衝突メッシュを、それぞれの全頂点を含むAABBへ保守的に近似した別worldも比較した。
箱は新たな接触を生み得るため、元メッシュと同等の物理モデルとは扱わない。形状を削って接触を見逃すための変更ではない。
衝突名・表面設定・慣性・見た目・センサー・制御値は維持し、元のAABBの8隅を全て内包することを検査した。

GUI・カメラ・録画・0.1 msを維持した初期シーンで、元メッシュ→箱→元メッシュを測定した。
RTFは0.07159→0.06744→0.06730。箱は元の前後平均の約0.971倍で、速度向上を確認できなかったため採用しない。
`collision_comparison.json`、`collision_box_variant.json`、各collision_*フォルダに生統計とSHAを保存した。
物理モデルの変更を導入する根拠は得られていない。
